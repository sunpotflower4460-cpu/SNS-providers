# SNS-providers 修正・改善指示書

確認日: 2026-11-20
対象: `main` の `4666f2b` と PR #19（`codex/iphone-daily-quality`）を統合したコード。実装を始める前に最新の `main` を取得し、各問題が未修正であることを再確認する。

## 目的と進め方

ローカルで候補を登録して交流を記録する日常利用と、クラウド接続後の承認・実行・記録を、一貫した動作にする。最初に承認対象と予算、次に実行結果の復旧を直し、その後に日次の使いやすさを整える。

以下の不具合は主に統合前の `main` にも存在していた。PR #19 のコンフリクト解消で新しく生じた問題という意味ではない。調査ではソース確認に加え、実際の TypeScript 関数、実 React コンポーネント、インメモリ SQLite、偽の API 応答を使って再現した。本番 SNS への送信や有料 API の呼び出しは実施していない。

各修正は「不具合を再現するテスト → 必要な変更 → そのテストと既存ゲートの確認」の順で進める。文字列がソースに存在するだけのテストを、状態遷移が正しい根拠にしない。既存の準備ウィザード、配色切替、ヘルプ、手動登録、データ移行、認証、利用額の制限を維持する。

## 今回の統合で対応した内容

- 6ファイルの衝突を解消し、最新 `main` の画面・準備ウィザード・ヘルプを維持。
- ローカルモードでの手動登録、不正 URL / 重複入力の説明、公式 SNS から戻ったときの結果記録と再起動後の復元を統合。
- プロフィールを確認しただけの場合と、実際にフォローした場合を区別。
- フォロー済み候補に再び「フォローした」を表示しない。`recordInteraction` でも重複フォローと本人未確認のフォロー記録を拒否し、回帰テストを追加。
- Safari のバックアップダウンロードを考慮し、保存開始と保存完了を混同しない文言へ変更。
- 古い例示用 AI ヒントを初期データ・復元データから除去。
- E2E を現在の導線に合わせ、既存のセキュリティ・配色・ウィザード検査を維持。
- 検証時点の依存監査に対応して Vite `7.3.8`、Wrangler `4.165.0`、Worker 型定義 `5.20261118.1` と関連 lockfile を更新。

この一覧にない以下の改善課題は、今回の競合解消に便乗して実装したものではない。次の作業として扱う。

## A1. 承認対象を相手・操作・本文へ固定する

**対象:** `src/MissionInbox.tsx` の先頭 `SocialActionCard`、`SocialActionCard` 内の `draftText` / `confirming` / `sendApprovedWrite`。

先頭カードに action ID の React `key` がなく、同じ位置に別の操作が入ると `confirming` 等が残る。下書きの初期化も `action.draft` / `action.aiDraft` だけに依存し、action 自体の同一性を見ていない。

### 再現済みの動作

1. A・Bの返信操作を用意し、Aの「返信する」で確認へ進む。
2. 確認中に「明日へ」を押す。
3. Bが先頭に出るが、Bにも確認画面と「送信する」が最初から表示される。
4. そのボタンを押すと、API モックには B の action ID で実行要求が届いた。

別の再現では、A・Bに保存済み下書きがない状態でA向けの文を入力し、新着Bを先頭にすると、Bの編集欄にA向けの未保存文が残った。勝手に送信されたという再現ではなく、確認対象・編集対象の切り替えを画面が正しく扱えていない問題である。

### 実装指示

- 先頭カードを `key={first.action.id}` で操作ごとに分ける。
- 承認対象として action ID、相手の不変 ID、投稿 / 会話 ID、本文の版を保持する。確認開始後に対象が変われば確認を解除する。
- 未保存の本文は action ID ごとに扱い、並び替えで別人へ移さない。キー追加だけで編集中の文を失う設計にしない。
- 延期・見送り・復元・受信更新・権限更新時の確認状態を明示的に管理する。送信処理中の対象変更も同じ規則で扱う。

### 受入条件

- Aを確認中にBへ切り替わると、Bは未確認状態から始まる。
- A向けの本文がBの編集欄や execute body に入らない。
- action ID が同じでも、送信先や本文が変われば古い承認は使われない。
- 実 React の再描画テストで、API モックへ渡る相手 ID・操作 ID・本文を確認する。

## A2. 予算設定の読み込み障害を、設定なしと区別する

**対象:** `worker/src/social/budgetCeiling.ts` の `loadUserBudgetCeilingUsd`、`resolveEffectiveBudgetLimit`、各有料処理の呼び出し元。

設定がない場合、不正値、SELECT エラーをすべて `null` にし、結果としてサーバーの既定上限を使える。実関数の検証では、保存済み上限 `$0` は通常 `0`、設定SELECTだけ失敗させると実効上限が `3` になった。台帳まで故障していれば別のガードが止めるが、設定テーブルだけの障害ではユーザーの低い上限を失う。

### 実装指示

- `found` / `missing` / `invalid` / `unavailable` を区別する。
- 予算設定を信頼できない場合、有料呼び出し前に停止する。設定なしの場合だけ、明示した初期値方針を適用する。
- クライアントから渡された大きな上限を、読み込み障害時の代わりにしない。
- 設定表示 API も、読み込み失敗を「設定なし」の成功応答にしない。
- 手動操作・準備処理・Cron が同じ判定を通るようにする。

### 受入条件

- 上限 `$0`・`$1`・未設定・破損値を分けて検証する。
- 設定SELECTだけ失敗し、台帳・予約SQLが正常でも有料provider呼び出しは0回。
- 無料機能を継続する場合も、無料であることが確定した経路に限る。

## A3. X の実呼び出し数と予算予約を一致させる

**対象:** `worker/src/social/prepare.ts`、`worker/src/social/x/lookup.ts`。

follow / unfollow準備ではlookupを1回分予約した後に、`/2/users/me` と対象ユーザーのlookupを実行する。ID検索からusername検索へfallbackするとさらに増える。自分のlookupが終わるまで `providerCallStarted` が立たない点も不整合。

SQLiteと偽providerによる再現では、上限 `$0.01`、lookup単価 `$0.01` で、HTTP読み取り2回に対して台帳は `$0.01` の1件だけとなり、prepareが成功した。これはコード内の会計モデルとの不一致の検証であり、現行のX料金を断定するものではない。

### 実装指示

- OAuthで保存済みの自分の不変IDを利用し、不要な `/users/me` を省く。
- 各実API呼び出しと追加fallbackを、対応する予約に成功した後だけ実行する。
- 呼び出し開始はfetch直前に記録する。送信後のタイムアウトでは、不明な費用の予約を消さない。
- 未設定の単価を無料と見なさない。

### 受入条件

- 残額1回分で2回目の有料読み取りが発生しない。
- 保存済み自分IDが使える場合 `/users/me` は0回。
- ID→username fallbackにも追加予約が必要。
- 開始前失敗は予約解除、呼び出し後の結果不明は保守的に保持する。
- `SOCIAL_WRITE_MODE=test` で費用処理を丸ごと飛ばさず、本番相当設定と偽providerで検証する。

## B1. 実行結果の復旧と関係記録への反映を一つの処理にする

**対象:** `src/MissionInbox.tsx`、`src/socialAction.ts` の `applyCanonicalServerActions` / `completeSocialAction`、`worker/src/social/execute.ts`、`reconcile.ts`、`lifecycle.ts`。

二つの問題を一緒に解決する。

1. execution IDを最初はuseRefだけに保存している。送信後・応答前にPWAが終了すると、照合用IDを失う。新IDは `ALREADY_EXECUTED` で拒否され、既存実行へ戻れないケースを確認した。
2. サーバーから `completed` を受け取ると、ローカル操作のstatusだけ完了にし、交流履歴・候補・Todayを更新しない。その後のcompleteもterminal判定で何もしない。検証結果は「action completed / 履歴0件 / 再適用しても0件」。

今回の再現ケースでは、サーバーガードが新しいexecution IDによる再実行を拒否した。二重送信を再現したわけではなく、主な問題は既存実行へ復旧できないことと、確定結果を記録できないことである。

### 実装指示

- 外部送信前に、ローカルaction ID、canonical action ID、execution ID、承認対象の対応を永続化する。
- 再起動後は保存済みIDで結果照合を行う。新IDを作って再送する方法で解決しない。
- 認証済み利用者がaction IDから既存実行を取得できる経路、または一覧に復旧情報を返す契約を追加する。
- canonicalの応答に、確定outcome、execution ID、外部結果ID、完了時刻、pending-follow等の意味を持たせる。
- 通常成功、結果再確認、起動時同期を同じ冪等なoutcome適用処理へ通す。
- 「actionが完了」と「この端末のCRMへ反映済み」を区別する。履歴は `socialActionId` / `executionId` 等で重複排除する。
- 未知の相手や別アカウントに実行履歴を結びつけない。既存の本人同一性チェックを維持する。

### 受入条件

- provider成功後・HTTP応答前に画面を破棄し、再起動しても結果を復旧できる。
- 成功はprovider write計1回、履歴1件、CRM更新1回、Today完了1件となる。
- 同じcanonical結果を繰り返し同期しても加点されない。
- 別端末、failed、unknown、pending followも意味を維持する。
- 送信直後のWorker停止では、証拠なしに成功扱いや再送をしない。

## B2. フォロー整理の判断と実際の解除を区別する

**対象:** `src/socialAction.ts` の `interactionActionFor` / `applyCompletedActionToCandidate`、`src/resultResolution.ts`、`src/MissionInbox.tsx`、結果シート。

SocialAction経由で解除APIが成功しても、`followedAt`・`followBack`等が残る。手動引き渡しで「フォロー解除した」を選ぶ経路も、`skipped`→操作のdismissになり、関係の解除を反映しない。旧Candidate経路と意味が揃っていない。

### 実装指示

- 「継続を選んだ」「実際に解除した」「今回は決めない」を別outcomeにする。
- API成功と公式アプリでの解除確認を、B1の共通outcome処理で反映する。
- 実際の解除で自分からのフォロー状態を更新する。相手から自分へのフォローは別方向の事実として、根拠なくfalseにしない。
- 会話履歴や関係の蓄積を削除しない。`stage`が関係の深さとフォロー状態を混同しないよう整理する。

### 受入条件

- API解除成功・手動解除確認の両方で「フォロー中」から外れる。
- 継続判断・単なる見送りではフォロー状態を変えない。
- 解除後に同じ解除候補がすぐ再提示されない。
- API失敗・結果不明では、証拠より先にフォロー状態を消さない。

## B3. 「明日へ」の期限をサーバーと画面で揃える

**対象:** `worker/src/social/lifecycle.ts` の `snoozeCanonicalAction` / `listCanonicalActions`、`repository.ts`、`executeGuard.ts`、`src/socialAction.ts`。

フロントは期限切れのsnoozedをreadyへ戻すが、WorkerはD1のsnoozedを戻さずexecute時に拒否する。同じ期限切れactionで「フロントready / canonical snoozed / guard INVALID_ACTION」を確認した。

### 実装指示

- canonical側で期限到来を原子的に反映する共通処理を用意する。
- execute前・一覧読み込みで適用する。完了・実行中・dismissed・期限切れ・再試行不可を不用意に復活させない。
- 「明日」の期限をクライアントとサーバーで共有する。クライアントの翌日0時とサーバーの単純な24時間後を混在させない。
- 復帰後も権限、投稿対象、DM返信期限等を再検証する。

### 受入条件

- 昼に延期→ローカル日付変更→再同期→同じ操作を1回だけ実行できる。
- 期限前には送れず、再起動・別端末でも一致する。
- 更新済みの完了操作や実行中操作がreadyへ戻らない。
- フロントとサーバーを個別に検査するだけでなく、保存→時間経過→再取得→executeまでつなぐ。

## C1. 1日の量を実際の残数として管理する

**対象:** `src/daily.ts`、`src/missionInboxModel.ts`、`src/App.tsx` のToday / `autoReplenishDemand`。

候補5人、合計2件・新規2件で始め、2人のフォローを完了すると次の2人が現れ、予定の分母が4になることを再現した。設定上限が表示窓のサイズとして使われ、当日の完了数が差し引かれていない。SocialActionの一覧にも同じ上限が適用されていない。

### 実装指示

- 本日の予定・完了・残枠を共通関数にし、Today、fallback queue、SocialAction inbox、自動補充で共有する。
- プロフィール確認、見送り、フォロー、返信、いいね、整理、自分の分析をどの分類へ数えるか明示する。純粋なプロフィール確認は実交流の完了にしない。
- 当日予定を固定する方式、または「上限−当日完了」を使う方式を選ぶ。自動で目標が増えないようにする。
- 新着受信を捨てず、追加の受信として表示し、通常の予定と分けて扱えるようにする。

### 受入条件

- 2件設定で2件終えれば完了となり、3件目が自動で必須残件にならない。
- SocialActionとCandidateの併用で二重計数しない。
- 日付変更でリセットし、同日再起動・復元では完了を保持する。
- 新着により達成表示が説明なく取り消されない。

## C2. バックアップを正規化する前に骨格を検証する

**対象:** `src/backup.ts` の `readBackup` / `normalizeAppState` / `validateAppState`、`src/BackupControls.tsx`。

次のデータを実際の `readBackup` に渡すと拒否されず、候補0件・履歴0件・既定の目的へ変換された。

```json
{"format":"social-mission-backup","version":1,"state":{"nonsense":true}}
```

上書きには既存の確認操作が必要だが、その確認に件数差分がなく、壊れたデータを正常な空バックアップと区別しにくい。

### 実装指示

- 正規化前にstateの必須骨格と、各versionの必須条件を検証する。
- 旧版移行による補完と、壊れた内容の欠落を分ける。
- 一部救済する場合は除外・欠落件数を表示し、通常復元と区別する。
- 復元前後の候補数・履歴数・目的・書出日時を比較表示する。復元直前のデータを戻せる手段も用意する。

### 受入条件

- 必須フィールド欠損、配列の型不一致、不正envelope、未知versionを拒否し、現データを変えない。
- 正常な旧版は明示的なmigrationで復元できる。
- 正常に0件のバックアップと、欠落したバックアップを区別できる。
- 正常データの書き出し→復元で候補・履歴を失わない。

## D. 運用と説明の改善

### D1. 検証済みコミットだけを公開する

`.github/workflows/ci.yml` と `deploy-pages.yml` / `deploy-worker.yml` は独立して開始する。Pagesは一部の検査を行うが、UX・回帰・E2E全体の成功を待たない。

- 共通の再利用ワークフロー等で、公開を同じSHAの必要検査の成功につなぐ。
- `workflow_run`を使うなら、成功したrunの `head_sha` をcheckoutする。後から進んだmainへ置き換えない。
- 検証用にE2Eを失敗させたときは公開されず、成功時は検証SHAと公開SHAが一致することを確認する。
- Workerの認証情報不足によるskipを、公開成功と区別してActions summaryへ表示する。「緑のチェックだけで準備完了」とする案内を修正し、実際の到達確認を完了条件にする。

### D2. Xの可否説明を実際の契約・権限へ揃える

`README.md` / `docs/MANUAL_GO_LIVE_CHECKLIST.md` はfollow・likeを設定次第で実行可能と説明する一方、`src/guideContent.ts` / `docs/SETUP_GUIDE_JA.md` にはAPI制限を断定した説明がある。`worker/src/social/capabilities.ts` の判定は主にflagとOAuth scopeから計算しており、同じ内容になっていない。

- 現行の公式仕様を一次情報で調べ、検証日・契約条件・必要権限を明記する。この監査だけで、外部API仕様のどちらの説明が正しいとは断定しない。
- capabilityを「利用可能 / 利用不可 / 未確認」で扱い、UI・README・ガイドを同じ情報に揃える。
- flagの存在だけで利用可能としない。契約や権限不足の状態では、実行可能と表示せず公式アプリへの引き渡しへ案内する。
- 使える操作・使えない操作・未確認の場合の表示を、契約と権限のモックで確認する。

### D3. 準備ウィザードを操作テストで守る

対象は `src/SetupWizard.tsx` / `wizardMemory.ts` / `setupSteps.tsx` / `HelpChat.tsx`。既存の文字列中心の検査に加え、Chromium・WebKitで次を確認する。

- 外部画面へ移動→再読み込み→元のステップへ戻る。
- 明示的に閉じたものは再読み込み後に自動で開かない。
- 最初からやり直すとチェック状態が適切に戻る。
- ヘルプを開く→Escape→元のステップへ戻り、背後も一緒に閉じない。
- 接続成功、キー不足、API不通をモックし、再入力・再設定を必要以上に繰り返させない。

### D4. 未処理一覧と履歴のページングを分ける

`worker/src/social/lifecycle.ts` の一覧は全状態混在で更新順200件。新しい完了履歴が200件あると、古いready / executingが一覧から落ちる。

- 未処理・結果不明を確実に取得し、完了履歴には安定したcursorを設ける。
- 201件以上・同時刻・古い未処理混在で、全未処理を取得できることを確認する。
- 更新中のページングで欠落・重複を起こさない。B1の別端末復旧にも同じ一覧仕様を使う。

## 推奨する実装単位

1. **承認と予算:** A1、A2、A3。相手と本文の取り違え、上限の緩みを先に防ぐ。
2. **実行・復旧・記録:** B1、B2、B3。共通outcomeを中心に一貫させ、D4も必要に応じて含める。
3. **日常利用とデータ保全:** C1、C2。1日の終わりが分かり、復元でデータを失わない状態へ整える。
4. **公開と案内:** D1、D2、D3。実装した挙動・検証・説明を揃える。

大きな1本の変更へまとめず、各単位で再現テストと修正結果が分かるPRにする。個別の実装でより適切な分割が必要なら、上の依存関係を維持して調整してよい。

## 検証と完了報告

必要な既存ゲートは次のとおり。各修正では影響のある回帰ケースを追加し、同じコミットに対して確認する。

```bash
npm ci --no-audit --no-fund
npm run typecheck
npm run security:check
npm run ux:check
node scripts/verify-regression-fixes.mjs
npm run pwa:check
npm run build
npm run dist:check
npm run test:e2e
npm audit --audit-level=high
npm --prefix worker ci --no-audit --no-fund
npm --prefix worker run typecheck
npm --prefix worker audit --audit-level=high
```

GitHub Pagesのsubpath / Worker origin入りのビルド確認も、既存CIで維持する。Playwright WebKitのオフラインreloadは既存テストがskipしているため、成功件数に含めない。iPhone実機のホーム画面起動、Safariダウンロード、キーボード、安全領域、VoiceOver、7日間の日常利用は別途確認が必要で、PCの自動テスト成功だけで完了扱いにしない。

完了報告には、対象ID、修正した挙動、再現テストの結果、検証したSHA、未確認の実機・外部連携範囲を記載する。テスト数を増やすこと自体を目的にせず、この文書の再現例が確実に防がれたことを示す。
